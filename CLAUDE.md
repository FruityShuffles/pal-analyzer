# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A **local, zero-setup Palworld combat-score analyzer**: the tool scores/ranks a player's owned Pals (species, level, IVs, passives) for combat and suggests an element-diverse party of 5. Pals can be entered manually **or** bulk-imported from the multiplayer server save (see Save ingestion). The deliverable is a single self-contained `pal_analyzer.html` the user double-clicks — no server, no runtime Python, no network. Python is used **only at build time** to bake reference data into the HTML and to convert save files into import JSON.

**Save ingestion (added once the server `Level.sav` became available).** The earlier "no owned-Pal data exists on this machine" premise no longer holds: the user obtained the server save. `ingest_save.py` reads it offline and emits import JSON that loads through the app's "⬆ Import JSON" button — the app stays fully offline. The primary import is the combined `out/pals-all.json`: every Pal carries an `owner` (player nickname, or the owning **guild's** name for Pals assigned to a base — base workers have no `OwnerPlayerUId` in the save and are attributed container → WorkerDirector → base → guild). Per-player files are still emitted; the app has an Owners chip filter that scopes both the ranked table and the party of 5. The old "do not add save-file reading" guidance is obsolete; save format details live in `docs/SAVE_INGEST.md`.

## Build pipeline

All build steps are stdlib-only (Python 3.8+, no pip installs). `build_id_maps.py`
feeds both the app's Trust data and save ingestion; `ingest_save.py` is otherwise
independent of the app build:

```bash
python import_gamedata.py     # game-file export -> data/pals.json + passives.json + breeding.json (offline)
python data/build_id_maps.py  # fetch ID maps -> data/id_maps.json (needs network)
python build_report.py        # bake species + passive + breeding JSON into pal_analyzer.html (offline)
python ingest_save.py         # Level.sav -> out/pals-<player>.json + out/ingest_review.md (needs an Oodle DLL)

python scoring_check.py       # combat-score formula lock
python breeding_check.py      # breeding algorithm + probability lock
node tools/js_check.js        # runs the shipped JS in a vm: cross-checks both, plus search invariants

python tools/breed_reach.py   # standalone experiment -> out/breed_reach.md (offline, not part of the app)
```

- **`data/pals.json` and `data/passives.json` now come from the game's own DataTables, not the wiki** (implemented 2026-07-25; `docs/GAMEDATA_EXTRACTION.md` records the plan and what actually happened). `import_gamedata.py` is stdlib-only and reads the JSON produced by `tools/gamedata/PalDataExport`, a read-only CUE4Parse dump of `Pal-Windows.pak` — see `tools/gamedata/README.md` for its prerequisites (a matching `.usmap`, an Oodle DLL, a side-installed .NET 10) and how to re-run it after a game patch. **Never write to the game install.** The extraction step is only needed when the game itself updates; `import_gamedata.py` alone is enough to regenerate the JSON from an existing export. `docs/DATA_SOURCES.md` records where every data file comes from, including the cross-checks (407 species rows agreed exactly with palworld-save-pal's independent datamine; the derived breeding table agreed with palcalc on all 44,552 shared parent pairs) and the licensing position for each source.
- `data/build_data.py` (the palworld.wiki.gg Cargo fetch, with its `SPECIES_OVERRIDES` / `PASSIVE_OVERRIDES` hand-patches) is **superseded and should not be run.** It is kept only as the fallback for a machine with no Palworld install. The wiki lagged the live game badly — the game-file import added 20 species and 19 passives the wiki never documented, corrected 10 species' base stats (Relaxaurus Defense 70 → 110, plus Relaxaurus Lux, Orserk, Grizzbolt, Jetragon, Lyleen, Lyleen Noct, Faleris, Faleris Aqua, Enchanted Sword), and made both override dicts unnecessary.
- Run `build_report.py` after **any** edit to `pal_analyzer_template.html` or the JSON. It fills in display-name-keyed Trust friendship stats from `data/id_maps.json` for any species record that lacks them (game-sourced records from `import_gamedata.py` already carry `friendship_*` straight from `DT_PalMonsterParameter`), then replaces the `/*__PALS_JSON__*/ {}` and `/*__PASSIVES_JSON__*/ {}` markers in the template with compact JSON. It hard-fails if the friendship map is absent. **`pal_analyzer.html` is generated — never hand-edit it; edit `pal_analyzer_template.html` and rebuild.**
- Run `build_id_maps.py` only when refreshing the internal-ID maps (after a game patch). Source is the palworld-save-pal project (keep its attribution); it maps the save's internal code IDs to display names for `ingest_save.py`, and still emits the `friendship` map that `build_report.py` falls back on. Then `ingest_save.py` reads `Level.sav` + the `<UID>.sav` player saves in the folder and writes `out/` (saves can be dropped anywhere and pointed at with `--level`/`--players`/`--out`; they don't need to sit at the repo root). Its `ingest_review.md` flags any species/passive present in the save but missing from `data/pals.json` / `data/passives.json`. **The fix for anything it flags is now re-running the game-data extraction, not hand-writing an override** — as of the 2026-07-25 import the report is empty. **The `out/*.json` files hold real players' Pal rosters — gitignored, never committed, never published (see Constraints).**

## Verifying the scoring formula

`scoring_check.py` is a Python mirror of the combat-score math and the canonical formula test:

```bash
python scoring_check.py      # asserts the Mammorest/Kitsun L1-vs-L50 crossover
```

The formula lives in **three places that must stay in sync**: `docs/FORMULAS.md` (spec/ground truth), `scoring_check.py` (Python mirror), and the `statHp`/`statAttack`/`statDefense`/`combatScore` functions inside `pal_analyzer_template.html` (the only runtime copy). If you touch the math, update all three and confirm both `scoring_check.py` and the in-page `console.assert` self-test still reproduce **151.0 / 899.6** (Mammorest) and **150.6 / 901.8** (Kitsun) at L1/L50, IV=0, no passives.

Condensing, combat Soul ranks, and Trust were implemented on 2026-07-19. `docs/AUGMENTS.md` remains the ground truth for mechanics, cost curves, thresholds, and save fields; Awakening and Work Speed remain excluded.

**Passive planner** (added 2026-07-25). A Pal's 4 passive slots can be bought into: ordinary passives (`rank` 1–3) cost gold, top-tier ones (`rank` 4) cost a one-time consumable. Two opt-in `state.assume` chips (`craft`, `premium`, both default **off**) make `TargetScore` use the best purchasable passive set instead of the Pal's actual one, via `planPassives()` — an exhaustive search over every ≤4 subset of (existing ∪ buyable pool), maximizing `(1+ΣAtk%)(1+ΣDef%)(1+ΣHp%)(1+BestElementBoost%)`. Purchase eligibility is `add_pal`, **not** `rank` alone (Legend/Lucky/Lunker/Whopper are low-rank but unbuyable). The element term makes the objective **species-dependent**, so the plan cache is keyed on elements too; first toggle on a 2,300-Pal roster costs ~1s, re-renders ~100ms. Greedy "take the biggest attack bonuses" is wrong here, and **the candidate walk is not prunable** — not by standalone `M` (mixed-sign passives like Sadist can still earn a slot) and not by componentwise domination (Ferocious +20 Atk survives beside Musclehead +30 Atk, because bonuses stack additively across four slots and the blank-Pal optimum takes both). Pruning dominated buyables is a tempting 4× speedup that costs up to 5% multiplier; it was tried and reverted, and `tools/js_check.js` now brute-forces the planner against an unpruned search to keep it out. `docs/FORMULAS.md` §4 has the counterexamples, `docs/AUGMENTS.md` §5 the mechanic. Two constants are player-reported assumptions rather than game data: `PASSIVE_GOLD` (50k/slot) and `PREMIUM_GOLD_EQUIV`. The planner scores passives by combat only, so it will evict work-speed passives that matter on base Pals — a known, surfaced limitation.

**Breeding path suggester** (added 2026-07-26; thesis corrected 2026-07-27; `docs/BREEDING.md` is ground truth). Answers "what should I *make*?" from the ingested roster. Its thesis is that inheriting a passive pays whenever getting it another way would cost you, and **`add_pal:true` does not mean free** — it means buyable, for gold (rank 1–3) or a scarce one-time consumable (rank 4). So `CHASE_POOL` is every `add_pal:false` combat passive (24, unconditionally) **plus** every buyable one clearing `CHASE_BAR = 1.20` (6 more, incl. Demon God ×1.365 and Diamond Body), and it is deliberately **tier-independent**: gating it on the assumption chips makes a passive un-chaseable in exactly the case where the only thing inheriting it saves is money. Inheriting pays in **score** when the child couldn't buy it, and in **cost** when it could — hence every row carries gold/tokens beside its score, ranked score → eggs → cost. The original version chased only `add_pal:false` passives, which made Demon God permanently invisible no matter how many parents carried it; `CHASE_BAR` is a tuning knob, not game data, because the pool drives the archetype count and the pair loop is quadratic in it (24 names → 137 carriers/~70k pairs; 30 → 346/~203k; all 52 → 933/~777k). `childSpecies()` is a three-rule port (same-species → unique combo → nearest `combi_rank` with the `+1` **inside** the floor), validated at **0 mismatches against palcalc's 44,552-row table**. Three things are easy to get wrong and are all load-bearing: the candidate pool excludes both `ignore_combi` species *and* every unique-combo child (183 of 301 survive); ties break toward the **higher** `combi_priority` and hit 12.4% of pairs; and the success event is `D ⊆ inherited`, not an exact match, because an unwanted passive is a 50k overwrite the planner already prices. **Availability is a matching problem, not a set union** — the first prototype's top answer was a Pal bred with itself, and 30 of the 80 species carrying an unbuyable have exactly one carrier, so archetypes track real entry ids and genders and phase 2 re-resolves the concrete pair. A plan may chase **at most one passive the child could simply buy** under the enabled tiers: that saving is additive while the egg cost is multiplicative, so one is a real trade and two never is. The per-species cap of 3 is applied by **dominance on (eggs, cost)**, not by rank, because an inherited-instead-of-bought passive ties on score and loses on eggs — the cost axis is the only place it can surface. **The search must never run from `render()`** — it is ~1.6–3.4s at depth 1 on 2,330 Pals depending on the chips and runs only from the button, with `renderBreedPanel()` repainting a cache and flagging staleness; `tools/js_check.js` asserts this and holds the timing budgets. Breeding is a **separate view** behind the sticky switcher at the top of `<main>` (`state.view`, `#viewRoster` / `#viewBreed`), because the ranked table is thousands of rows tall and anything below it is unreachable. Target level, assumption chips and owner chips are mirrored into both views over the same state — render any new shared control into both containers.

**Breeding reachability experiment** (added 2026-07-28; `docs/BREED_REACH.md` is ground truth). `tools/breed_reach.py` is a **standalone offline script, not part of the app** — no template, build or `data/` changes. It inverts the suggester's question: given that **Cawgnito and Sibelyx already carry Lucky + Demon God + Diamond Body**, what is reachable and what does it cost? Passive selection is out of the model; the payload is assumed to ride along. **Cost is unique breeding pairs, not generations** — parents survive breeding, so a species used twice is bred once, and depth doesn't even order targets correctly (one depth-8 target is 17 pairs, a depth-5 target is 5). Two traps are load-bearing and both produced real bugs: **every step needs at least one carrier parent** (treating seeds and clean partners as one "free" set silently emitted `Blazehowl* × Majex* → Bulldosu`, two passive-free parents making a child that inherits nothing), and **a plan must tag each parent as owned-clean or bred** (a plan can use the owned clean Ribbuny as a partner while separately breeding a carrying Ribbuny; bare names read as a dependency cycle). Plans are dicts `{species: ((a, a_bred), (b, b_bred))}`, never sets of species. `gender_blind_combos()` strips the gender pins `breeding_check.child_species` would otherwise require — **`breeding_check.py` stays a locked mirror; rewrite the index it consumes, not its semantics.** The search is a heuristic upper bound (Steiner-tree flavoured); `--verify` replays every plan and brute-forces a synthetic table, and `docs/BREED_REACH.md` §5.3 has the exhaustive carrier-set enumeration that proves optimality exactly for targets up to ~5 pairs. **The clean-partner pool is the whole puzzle** — it defaults to every owner in the roster (`DEFAULT_OWNERS = []`) and narrows with `--owners`; 22 species under a two-player subset, and `--partner-value` (which single clean Pal to go acquire) is the most actionable output. Probability, gender and entry-level availability are all deliberately out of scope, unlike the shipped suggester.

**Wishlist / breed-to-target solver** (added 2026-08-29; `docs/WISHLIST.md` is ground truth). The third breeding question, and the inverse of the suggester: you name the Pal you want and the 1-4 passives it must have, and it returns the single cheapest route from the Pals you can actually put in a pen, measured in **total expected eggs**. Inverting the question is what makes it affordable -- with at most 4 named passives an intermediate's whole relevant state is `(species, wanted mask, junk count)`, ~24k nodes rather than every passive combination. Three things are load-bearing. **A wish is a spec and the solver does not second-guess it**: every named passive is bred, with one liberty -- a rank 1-3 `add_pal` passive is bought for 50k, which is noise against one extra hatch. There is deliberately no premium option, because if you'd spend a token on a passive you simply leave it out of the wish; this also means a 4-passive wish usually collapses to breeding *two* things, since Musclehead/Burly Body/Ferocious/Heavyweight are all 50k buys. **Junk is a price, not a wall** -- a dirty parent only enlarges the pool the wanted passives are drawn from, so where the only Legend carrier is `Legend + 2 junk`, using it dirty costs **4.0 eggs and cleaning it first costs 20.5**; requiring junk-free intermediates quotes 20 eggs for a 4-egg job. It flips only at `|D| = 4`, where the final pool must be exactly 4 (10 eggs; m=5 -> 50, m=6 -> 150), so junk is a **Pareto axis on cost, never a filter** and `acceptProb(m, k, maxExtras)` generalises `inheritProb()` with a pickiness dimension (mirrored by `p_accept()` in `breeding_check.py`). Junk on the *target* is free, since an overwrite costs the same 50k as filling an empty slot. **Gender is not a node dimension**: two bred intermediates are both unhatched so neither is targeted; only a bred parent paired with a *gender-locked* owned one pays `1/P(gender)`. The search is **anytime** -- iterative broadening, beams widening fourfold, a running cost bound from the first cheap route, and a bucketed beam (sorting on eggs alone starves the 3- and 4-passive nodes that are the only ones near the goal). It reports `converged` or `budget` honestly and **must never run from `render()`**, only from a wish's Solve button. Negative answers name their cause: the uncarried passive, that the species fits in no breeding pen at all, or that it is never the child of two *different* species (28 species, all `ignore_combi`, incl. Frostallion, Jetragon, Blazamut Ryu -- checked up front, so it is instant rather than a 10-second dead end).

**Species that cannot be bred at all** (added 2026-09-03; `docs/BREEDING.md` §1 is ground truth). A **third** exclusion, and the only one on the *parent* side: **Astralym, Boltmane, Dragostrophe and Panthalus fit in no breeding pen.** `ignore_combi` is not this rule -- it bars a species from being a rank-rule *child* while leaving Frostallion and Jetragon perfectly legal parents, so reusing it either way is wrong, and before this the suggester and the wishlist solver happily offered an owned Panthalus as a parent. The game has **no "cannot breed" field**; these four are the only shipped species with zero work suitability, so they can never be assigned to a base and a breeding pen is a base structure. `import_gamedata.py` derives `can_breed` from that and **prints the four names on every run** -- a patch that moves the set must be loud, because it is an inference about game behaviour, not a datamine. The gate deliberately stays **out of `childSpecies()`**, which is the locked mirror validated at 0 mismatches against palcalc's 44,552 pairs; it sits one layer up at the places a parent pool is built -- `buildArchetypes()`, `wishKids()` (the wishlist's chokepoint, so it also covers the partner pool and `wishCrossReachable()`), `cleanPartners()`, the wishlist's target check, and `clean_pool()` in `tools/breed_reach.py`. All four are already `ignore_combi` and are no unique combo's child, so nothing but the parent side changes.

Formula gotchas (see `docs/FORMULAS.md` for why):
- Defense base constant is **50**, not 100 (the wiki article has a typo; 50 is correct).
- Structure is `floor(floor(base + slope·Level·(1+IV%)) · (1+PassiveBonus%) · (1+SoulBonus%) · (1+CondenseBonus%))` — two nested floors. Multiplier classes multiply each other inside the single outer floor.
- `IV% = TalentInt · 0.3 / 100`; passive bonuses are **additive** across a Pal's passives, stored as percent (e.g. `10`) and divided by 100 at use.
- **Max-HP passives are rare but real**: the wiki data had none (hence the old "`hp_pct` is always 0" note), but the game files list two — God of Destruction (Max HP −50%) and World Tree Seedbed (−20%). `passiveBonuses()` sums all three stats. Only effects targeting the Pal (`ToSelf`/`None`) count; `ToTrainer` ones buff the *player* and are dropped at import.
- **Element boosts are a separate multiplier class, not part of `PassiveBonus%`.** They raise damage dealt, never the displayed Attack stat, so `computeAt()` keeps `atk` as the game's number and applies `elementBonus()` only inside `combatScore`. The bonus is the **max** over the Pal's own elements of the boosts naming that element (one element per attack move), not a sum across elements; boosts naming the *same* element do add. Off-element boosts are worth zero. `ElementResist_*` stays excluded — it keys off the incoming attack.
- Trust changes the effective species stat to `species_stat + friendship_stat · trustRank` before level scaling.

### Verifying the app's JS logic without a browser

There's no headless browser installed. To exercise the real runtime code (scoring, party dedupe, persistence), extract the `<script>` from `pal_analyzer.html` and run it in Node with minimal `document`/`localStorage` stubs inside a `vm` context. Note: top-level `let` bindings (`state`, `optimizeBy`, `activeElements`) are **not** on the context object — append an epilogue in the same scope to expose them (e.g. `globalThis.__getState=()=>state`). Function declarations (`computeAt`, `decorate`, `normalizeEntry`, `passiveBonuses`, `save`/`load`, `renderParty`) attach to the context and are directly callable.

## Architecture

**Data flow:** game DataTables via `tools/gamedata/PalDataExport` → `import_gamedata.py` → `data/pals.json` + `data/passives.json` + `data/breeding.json` → `build_report.py` → `pal_analyzer.html` (data baked inline) → runs entirely in the browser over `localStorage`. `build_id_maps.py` feeds `ingest_save.py`'s ID → display-name mapping on a separate track.

- **`data/pals.json`** — `{ species: { hp_stat, attack_stat, defense_stat, elements: [1-2 tags], friendship_hp, friendship_attack, friendship_defense, combi_rank, combi_priority, ignore_combi, male_probability, variant, can_breed } }`. The last six are breeding fields (`docs/BREEDING.md`); `can_breed` is the only field in the file that is an **inference** rather than a datamined value (`docs/DATA_SOURCES.md`). From `DT_PalMonsterParameter`: `Hp` / `ShotAttack` / `Defense` (the displayed "Attack" is ShotAttack — no Pal passive touches MeleeAttack) and `ElementType1/2` in primary-first order, remapped `Electricity→Electric, Earth→Ground, Leaf→Grass, Normal→Neutral`. One record per **tribe**, keeping the row whose key *is* the tribe id — that drops `BOSS_`/`PREDATOR_`/`GYM_`/`RAID_`/oilrig/quest variants, reproducing the old `palVariant='Normal'` filter. Rows with no English name (unreleased content) are skipped.
- **`data/passives.json`** — `{ passive: { attack_pct, defense_pct, hp_pct, rank, add_pal, lottery_weight, element_boosts, description, effect_summary, effects } }`. `element_boosts` is `{element: pct}` from the `ElementBoost_<Element>` effect rows (the element is in the effect-type name, not `TargetElementType`); `ElementResist_*` is excluded from **scoring** on purpose — it keys off the incoming attack — but is still carried in `effects`. From `DT_PassiveSkill_Main`, filtered to `Category == SortDisplayable` (the game's own "the UI shows this on a Pal" flag — the other ~1790 rows are test/internal/equipment-only). Only `ShotAttack` / `Defense` / `MaxHP` and `ElementBoost_*` legs landing on the Pal feed scoring.
- **Every effect is now recorded, not just the scored ones** (2026-09-01; `docs/DATA_SOURCES.md` is ground truth). `effects` is one entry per populated `EffectType1..4` slot — `{type, value, unit, scope, label}`, 167 legs over 51 distinct effect types — so Work Speed, work suitability, SAN, hunger and the flinch/knockback immunities are machine-readable instead of buried in prose. `unit` is `percent` / `flat` (from `DT_PassiveSkillEffectCondition`'s `bIsFixedValue`, the game's own answer — don't hand-maintain a list) / `flag` (value is exactly `0.0`; the label *is* the effect). `scope` is `pal` / `pal_and_player` / `player` (a `ToTrainer` leg buffing the player, kept out of the Pal's score) / `structure` (`ToBuildObject`). **`import_gamedata.py` reports any effect type it has no label for — that report must stay empty; a game patch adding an effect type is meant to be loud, not silently humanised into "Lean Back Invalid For Passive Skill".**
- **Two text fields, because neither is trustworthy alone.** 94 of the 115 ship an authored English `description` from `DT_SkillDescText_en` (via `OverrideDescMsgID`); the game composes the other 21 at runtime and so do we. That authored copy sometimes omits a leg (Noble/Fine Furs/Shabby each hide a buy-price half) and once contradicts the data — Otherworldly Cells calls an `ElementBoost_Electricity +15` row "Lightning damage reduction". `effect_summary` is rebuilt from `effects` and is always complete; `description` keeps the prose, which carries conditions the rows don't encode ("when assigned to a Breeding Farm"). The app shows the summary first and the prose after it when they differ.

- **`data/breeding.json`** — `{ unique: [{a, ga, b, gb, child}] }`, the 253 unique parent-pair overrides from `DT_PalCombiUnique`. `ga`/`gb` are almost always `""`; only Katress × Wixen pins genders.

**The app (`pal_analyzer_template.html`)** is one file, vanilla JS, no dependencies. Key pieces:
- **State** is a single `state = { version, targetLevel, assume:{condense,souls,trust}, pals: [...] }` object, auto-saved to `localStorage` key `palAnalyzer.v1` on every change. Entries include `condense`, `soulHp`, `soulAtk`, `soulDef`, and derived `trust`, all defaulting to 0. `normalizeEntry()` is the validation/clamp chokepoint — all writes (form, import, load) pass through it.
- **Two scores per Pal**: `CurrentScore` uses the entered level and actual augments; `TargetScore` uses the adjustable target level (default 80) and assumed-max augment toggles; `Headroom = Target − Current` is the "worth investing?" signal. Rank order is level-dependent, which is the whole point of showing both.
- **Party-of-5** dedupes by **exact** element signature (sorted element list, so `{Fire,Dragon}` and `{Fire}` are distinct; two pure-Fire Pals conflict), keeps the highest-scoring Pal per signature, and has a Current-vs-Target optimize toggle.
- **Owner filter**: entries carry an optional `owner` (player or guild); dynamic chips filter by owner and — unlike the element/text filters, which are table-only — also scope the party of 5. Importing a file with a top-level `player` stamps it onto owner-less entries.
- **Wishlist** entries are `state.wishlist = [{id, species, passives}]` through `normalizeWish()`, and the view is the third segment of the same sticky switcher. Wishes deliberately outlive the roster: import only replaces `state.pals`, and `out/` is re-ingested often.
- Species/passive inputs use native `<datalist>` for zero-dependency autocomplete.

## Repository

Public on GitHub since 2026-08-30: **`FruityShuffles/pal-analyzer`**, MIT, default branch `main`
(`origin` is set and `main` tracks it). Anything committed here is world-readable, which is what
the `.gitignore` entries for `saves/`, `out/`, `tools/gamedata/vendor/` and `tools/gamedata/export/`
are defending — the first two are real player data, the last two are the user's own game files.

- **`README.md` is the user-facing front door and is not generated.** It documents the three views,
  the save-import flow, the rebuild pipeline and the three check commands. A change that adds a view,
  renames a script, or alters the build steps makes it stale — update it in the same commit. It also
  carries the licensing position: MIT covers this project's code, while the extracted DataTables under
  `data/` remain Pocketpair's and are excluded from that grant. Don't quietly widen the MIT claim.
- `.gitattributes` sets `* text=auto eol=lf`, so the repo is LF even though development is on Windows.
  Expect `git` to report CRLF→LF conversion on checkout; that is not a diff to "fix".
- **`CLAUDE.md` and `AGENTS.md` are the same document**, for Claude Code and Codex respectively; only
  the first three lines differ. They drifted apart once and it was the dangerous kind of drift — the
  Codex copy went on presenting the superseded `data/build_data.py` wiki fetch as *the* build pipeline
  for five weeks after the game-file import replaced it, while carrying accurate notes on newer
  features, so it read as current. Port every change to both in the same commit.

## Constraints

- `pal_analyzer.html` must stay **fully self-contained and offline** — no CDN, no external `src`/`href` to scripts/CSS, no `fetch`/XHR. The only allowed external URL is the inert palworld-save-pal attribution link in the footer (the wiki link went away with the wiki data).
- **Know which artefacts carry real player data and which don't.** `pal_analyzer.html` is *generated* and bakes only the three reference DBs (`build_report.py` injects `__PALS_JSON__` / `__PASSIVES_JSON__` / `__BREEDING_JSON__` and nothing else) — the user's roster lives in `localStorage` at runtime and never enters the file, which is why it ships in the public repo. The real player data is **`out/*.json` and `saves/`**: gitignored, never to be committed, and never to be published as a Claude Artifact or pasted into a report. `out/` holds other people's rosters, not just the user's.
- Species/passive data is extracted from the game's own files, so the wiki's CC BY-SA 4.0 terms no longer apply to it — but `data/*.json` records the game build it came from, and the palworld-save-pal attribution stays wherever `data/id_maps.json` is used. Keep both. The wiki link is gone from the footer along with the wiki data; don't remove the remaining attribution without checking what still sources from where.
- Scope is deliberately narrow (see the plan): stats + passives + implemented combat augments only, no active-skill/type-advantage math. **Breeding was added 2026-07-26** (`docs/BREEDING.md`) and the **wishlist** on 2026-08-29 (`docs/WISHLIST.md`); together they are the sanctioned exception to "no suggestions for un-entered Pals" — it proposes Pals you don't own, but only ones reachable from Pals you do. Don't expand further without asking.
